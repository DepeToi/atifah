## 发现详情

### [Blocker] atifah-common/common-security/src/main/java/com/atifah/common/security/crypto/ConfigCipher.java:124 — SEC-02 — 主密钥格式与来源没有按 ADR 强制校验

- 证据：`toSecretKey` 只拒绝空白值，随后直接对任意 UTF-8 字符串做 SHA-256；没有 Base64URL 解码，也没有校验解码后是否为 32 字节。类注释还写明“口令长度不限”，与 ADR 0005 §1 的“32 字节随机数，base64url 无填充”冲突。现有测试使用 `unit-test-master-key` 和 `another-key` 均能正常完成加解密。另 `resolveMasterKey()` 在任意环境无条件接受同名 JVM system property，而 ADR 只允许本地调试使用。
- 影响：运维误配 `CONFIG_ENC_KEY=password` 等弱值不会被拒绝，持有配置密文的人可离线猜测弱主密钥；生产使用 `-DCONFIG_ENC_KEY=...` 还会使密钥出现在进程参数/诊断信息中。
- 建议：使用 `Base64.getUrlDecoder()` 解码并严格要求 32 字节，格式错误时带 `CONFIG_ENC_KEY` 名称 fail-fast；生产只接受环境变量，system property 仅允许显式 local/test 场景，或直接移除。同步修改注释、ADR 示例与测试密钥生成方式。

### [Major] atifah-common/common-security/src/main/java/com/atifah/common/security/crypto/ConfigCryptoEnvironmentPostProcessor.java:36 — SEC-02 — 错误密钥或篡改密文不会在启动阶段 fail-fast

- 证据：主密钥存在时，处理器只置顶一个延迟解密属性源，没有在 EnvironmentPostProcessor 阶段校验任何 `ENC(...)`。定向探针使用错误密钥时结果为 `WRONG_KEY_POST_PROCESS_RETURNED=true`，第一次读取该属性才 `WRONG_KEY_FIRST_READ_FAILED=true`。
- 影响：错误主密钥、被截断或篡改的密文可以随应用启动；若对应配置不是启动期 bean 的必读项，服务可能进入就绪状态后在运行中才失败。这与 ADR 0005 §3“解密失败：启动失败”不一致。
- 建议：主密钥存在时遍历可枚举属性源，对所有 `ENC(...)` 做一次启动期验证性解密；失败信息只包含属性名与 `CONFIG_ENC_KEY`，不得包含值或密钥。增加错误密钥、篡改、截断的 postprocessor 负向测试。

### [Major] atifah-common/common-security/src/main/java/com/atifah/common/security/crypto/ConfigCryptoPropertySource.java:77 — SEC-02 — 解密后的合法明文会被再次当作占位符解析

- 证据：属性源返回解密后的 String 后，Spring 环境解析器还会继续处理其中的 `${...}`。定向探针对一个包含字面量 `${SECRET_FRAGMENT}` 的明文加密后读取，输出 `DECRYPTED_PLACEHOLDER_RESOLVED=true`，即密文解出的密码被环境变量再次替换。
- 影响：包含 `${...}` 字面片段的合法数据库/Redis 密码会被静默改写或解析失败，造成认证失败；安全配置的“解密后原样使用”没有被保证。
- 建议：确保解密结果不参与第二次占位符展开，或对该场景采用可验证的转义/包装机制；增加“密文解密后的 `${...}` 必须保持字面值”的回归测试。

### [Major] atifah-common/common-security/src/main/java/com/atifah/common/security/crypto/ConfigEncryptTool.java:44 — SEC-01 / SEC-02 — 加密工具的明文输入直接来自命令行参数

- 证据：`encrypt` 读取 `args[1]`，Javadoc 与 `deploy/nacos/README.md:51` 都要求执行 `... encrypt '真实口令'`。注释只说明主密钥不接受命令行参数，却没有处理待加密明文同样会进入 shell 历史、进程列表和 CI 命令回显的问题。
- 影响：按文档操作即可把生产口令暴露在本机命令历史或进程诊断中，削弱配置密文对凭据的保护。
- 建议：明文改为从无回显终端或 stdin 读取，文档示例不得把真实口令作为 argv；增加仅从 stdin 读取明文的 CLI 测试。

### [Minor] TODO.md:177 — DOC-02 — P0-5 跟踪项与本 PR 的实际完成状态不一致

- 证据：同一 PR 在 `docs/rules/security.md:26-29` 已补充“配置密文”SEC-02 条款，但 `TODO.md` 的新增证据仍写“尚未约定”，动作清单也保持未勾选。
